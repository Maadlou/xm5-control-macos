XM5 and XM6 compatibility

Keep device layouts, local drafts, and confirmed state separate

Tasks 1-7 are implemented. Connection and noise-state readback were observed on XM6 firmware 3.1.5; full real-device acceptance remains pending.

Created: 2026-10-27 · Updated: 2026-10-27 · PR: None · Branch: xm6-compatibility-v0

Context and outcome

Discovery alone could not extend this app to XM6. The old EQ model always emitted six values. The user requires existing XM5 controls and saved profiles to keep working.

The implementation adds negotiated device capabilities, separate EQ formats, safe sessions, and model-aware views. It preserves the app identity, preference domain, keyboard shortcut, original XM5 packet values, and legacy profile backups. Hardware compatibility is not inferred from simulated tests.

Architecture and operation

  1. Discovery selects a supported connected device, then checks command-table support and advertised functions. The revision remains diagnostic metadata.
  2. The view edits a draft for the active layout. The controller validates and debounces the write.
  3. A matching response to that operation's query confirms the device state. An ACK does not.
  4. Profiles remain local and layout-specific. Legacy records import once while original data stays unchanged.

Decisions and reasons

D1 · Accepted: separate specifications

XM5 keeps Clear Bass plus five bands, range -10...10, and offset +10. XM6 uses ten bands, range -6...6, and offset +6. A broader name filter alone would emit incompatible packets. The cost is explicit metadata and separate validation.

D2 · Accepted: conservative capabilities

XM6 needs known advertised feature families. XM5 retains existing optional defaults. Model-name assumptions could enable unsupported writes. Unsupported EQ therefore leaves working noise controls available. The cost is limited support for unknown feature families.

D3 · Accepted: new storage key and raw backups

Version 2 keys drafts and profiles by layout instead of rewriting legacy storage. Records recover independently. Damaged or unknown-version version 2 data becomes read-only. The cost is explicit recovery before disk saves; in-memory draft edits still work.

D4 · Accepted implementation choice: optional save result

The planned unconditional profile return could imply success for blocked saves. Saving returns nil on failure, and the editor reports storage errors. Callers must handle failure explicitly.

D5 · Accepted: own each query response

A readback-issued boolean let an old A response confirm a newer A request after an intervening B write. One outstanding query per feature retains its owner across edits, including manual and poll queries. Missing replies require fresh-session Sync rather than ticket reassignment. The cost is serialization and an explicit resync after ambiguity.

D6 · Accepted: retain local intent and reported evidence

Automatic adoption after timeout erased failed drafts. Dirty layouts now retain edits through failures and unrelated actions. Successful confirmation or explicit EQ Sync adopts device values. A preset-only Custom response cannot establish a curve or display Synced. The cost is separate draft, pending, and reported-curve state.

D7 · Accepted correction: separate family and opaque revision

The real headset returned revision 0x03003032 with table 1 enabled. Requiring literal 2 rejected a valid connection. The controller now requires the advertised table and validated capabilities, as the reference client does. Diagnostics retain the raw revision. The captured reply is a regression fixture. The cost is relying on table and payload contracts rather than a misleading numeric-family comparison.

Evidence and limits

At commit 1536241, the connection-fix suite passed 48 unit tests and 15 UI tests. The corrected Release build passed. The website production build passed earlier in this implementation. The Release signature verified, with macOS 14.0 minimum and the existing bundle identifier. Independent review found three Important state defects; regression tests reproduced each before the fixes.

  • Session and query ownership
  • Draft and confirmation presentation
  • Storage and legacy migration
  • Pinned references and observed verification
  • Pending manual acceptance

Simulated ten-band layout was visually checked. This HTML's structure and links were checked; its browser rendering was not checked. The corrected Release reached ready state on the physical XM6, firmware 3.1.5, and read Ambient mode. This verifies the handshake and a state read. It does not establish ANC/EQ write acceptance or XM5 hardware regression results. Both models still need the manual checklist, including sleep/reconnect and multipoint. No release was published.
